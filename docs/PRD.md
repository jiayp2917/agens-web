# 产品需求文档

## 1. 文档定位

本文定义 `agens-web` 首个可发布版本的玩家产品边界和验收标准。它不描述
数据库表、部署步骤、模型供应商差异、测试脚本或历史治理过程；这些内容分别以
`ARCHITECTURE.md`、`RUNTIME_FLOW.md`、`security.md`、`PROJECT_AUDIT.md` 和
`NEXT_GOVERNANCE_BACKLOG.md` 为准。

当前首发内容版本为 v2。v3 是已实现但尚未定版的后续内容升级，不是首发前置条件。

## 2. 产品目标

为中文玩家提供可持续游玩的 Web 文字修仙模拟器：玩家创建角色，在规则确定的
修仙世界中，以固定语义的四项选择推进人生、剧情和结局。

产品应做到：

- 无需配置模型 Key 即可开始游戏。
- 角色成长、风险、寿元、奖励、死亡和结局可理解且可持续保存。
- 模型只负责叙事表达；规则始终决定游戏结果。
- 模型暂不可用时，玩家能明确决定如何继续，而不会丢失或隐式改变游戏状态。

## 3. 用户与角色

| 角色 | 目标 | 可用能力 |
| --- | --- | --- |
| 访客玩家 | 立即体验游戏 | 创建短期访客局并游玩；使用系统模型 |
| 注册玩家 | 保存并持续游玩 | 创建、读取、继续和结束自己的存档；个人模型 Key 的浏览器会话化是后续目标，不是当前 v2 定版已完成能力 |
| 运营者 | 提供默认游玩能力 | 配置系统模型及其 Key；该能力不属于玩家界面或玩家 PRD 的功能承诺 |

系统模型由项目提供，作为所有未启用个人模型的玩家的默认叙事来源。玩家不需要
知道 Key、模型厂商或网络地址。

## 4. 核心玩法

### 4.1 开局与选择

- 游戏模式只提供 A/B/C/D 四项选择：A 稳妥、B 机遇、C 风险、D 气运。
- 不提供自由文本行动入口，不提供常驻战斗按钮、HP 或 MP 面板。
- 开局创建角色和世界背景，随后从 16 岁开始进行选择。
- 境界顺序为练气、筑基、金丹、元婴、化神、合体、大乘、渡劫、飞升。
- 玩家可查看角色的可见状态、世界情报和已发生事件，但前端不能修改权威游戏状态。

### 4.2 规则与叙事

- 规则先结算每回合的权威结果，再由模型生成符合该结果的中文叙事和四项选择。
- 模型、玩家浏览器和审核逻辑均不得修改年龄、寿元、境界、伤势、奖励、死亡、
  剧情绑定或结局。
- 同一存档、随机种子和选择序列必须得到相同的权威状态轨迹。

### 4.3 存档与并发保护

- 访客局可在其有效期内继续；注册玩家可保存、读取和继续自己的局。
- 每次会话变更都以版本号和请求标识保护。重复点击返回原结果，过期页面提交返回
  冲突提示而不覆盖较新的游戏状态。
- 旧存档按照其记录的内容版本继续解析，不能静默升级或改写历史剧情。

## 5. 模型使用策略

### 5.1 系统模型

- 默认使用运营者配置的系统模型，系统 Key 仅由服务端使用并保存在项目的受控配置中。
- 系统 Key 不得出现在玩家界面、API 响应、浏览器包、游戏存档、会话快照或日志中。
- 系统模型的供应商、地址、模型名和密钥管理属于运营与架构配置，不作为玩家产品
  设置或玩家 PRD 的承诺。

### 5.2 个人模型（后续目标，尚未实施）

个人模型不是首发游玩的必要条件。已确认的目标是：浏览器只在当前 `sessionStorage`
会话保存个人 Key，每次请求临时传递，服务端不得写入 PostgreSQL、存档、会话快照、
日志、错误报告或环境变量。

当前实现仍将登录用户的个人 Key 加密后写入 `user_model_configs`；因此不能将上述目标
描述为已完成，也不能把它纳入本机 v2 系统模型定版的通过结论。改造范围和兼容要求见
`NEXT_GOVERNANCE_BACKLOG.md`。

## 6. 模型失败处理

模型失败、超时、拒绝、非 JSON 或契约不完整时，系统必须保存待处理失败和已冻结的
规则结果，但不得推进 `game_turns`、规则随机数或权威游戏状态。

玩家必须明确选择以下一种处理方式：

1. 重试模型：只重新请求同一个已冻结结果，不重新结算规则。
2. 使用本地故事：在同一个已冻结结果上生成本地叙事和 A/B/C/D 选项后继续。
3. 结束本局：正常进入本局结束流程。

系统不得自动转入本地故事，也不得把本地故事、补齐文本或失败恢复计为模型严格成功。

## 7. 内容版本与发布范围

### 7.1 v2：首发版本

- 新局默认创建 `story_version=2` 的九阶段、约 90 回合内容。
- v1 的 60 回合旧档继续可读取和游玩。
- 首发验收只要求默认系统模型在 v2 的开局、短流程、存读档、重试、幂等与冲突处理
  中满足既定严格契约。

### 7.2 v3：后续内容升级

v3 保留九阶段内容，并新增两条命数承诺、路线后果、motif 去重和 `post_arc`。它必须
在下列条件全部完成后，才可改为新局默认版本：

- 默认系统模型完成严格开局、20 回合浏览器 smoke、三条固定完整场景和一个 95 回合
  `post_arc` 场景。
- 所有验收回合均为最终 strict，无 fallback、repair、recovery、状态冲突、英文或协议
  结构残留。
- 权威状态轨迹与无模型规则回放一致，存读档兼容 v1、v2、v3。
- 从开场、中段和收束抽取的九个脱敏快照完成内容审核，P0/P1 为零。

v3 未满足上述条件时，首发默认版本保持 v2，不得以已有代码或离线规则结果替代玩家
可见的真实模型验收。

## 8. 首发验收标准

首发前应确认：

- 新玩家无需个人 Key 即可使用系统模型开始 v2 游戏。
- 注册玩家的存档、保存、读取、刷新、重复点击和过期版本冲突行为正确。
- 个人 Key 的浏览器会话化不属于本机 v2 系统模型定版范围，当前实现差异必须保留在 backlog，不能声称已完成。
- 模型失败不会修改权威回合，且三种玩家处理方式均可恢复或结束游戏。
- 可见内容为完整中文叙事和四项具体选择，不泄露协议字段、内部提示或 Key。
- v1/v2 旧档可继续至少一回合；v3 旧档兼容不回归。

## 9. 明确非目标

- 本期不承诺移动端 App、CLI/REPL、自由文本行动、玩家对战或复杂资源战斗界面。
- 本期不把模型供应商切换、模型能力排名或双模型对比作为玩家功能。
- 本期不把 v3 定版、生产部署或公开发布作为 v2 首发 PRD 的已完成事实。
- 本期不向玩家暴露系统模型管理、运营密钥、基础地址、部署网络或数据库管理功能。

## 10. 后续路线

首发 v2 稳定后，下一内容里程碑是 v3 严格验收与默认版本切换。后续是否扩大个人
模型的保存期限、支持范围或运营管理界面，应先形成独立产品需求和安全评审，不从
本 PRD 隐式推导。
