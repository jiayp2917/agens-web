## 1. 总体目标

将项目持续推进为可供真实玩家使用的第三人称修仙编年史 Web 游戏：

- 世界、人物、事件和长期因果持续发展，而不是每回合临场拼接。
- 规则结算、模型叙事、玩家可见文本、存档和数据库状态一致。
- 桌面端与移动端具备完整、可访问、可恢复的交互体验。
- 事务、幂等、迁移、备份、安全和回滚边界能够支撑真实用户。
- 重复实现、冗余结构、废弃内容和复杂度热点围绕主流程持续下降。
- 测试、浏览器、部署和文档只陈述当前可验证事实。

项目不进行无收益的架构重写。每个批次只交付一个可描述的行为目标，并同步完成必要代码、测试、验证和文档。

## 2. 稳定边界

### 2.1 产品边界

- 保持 FastAPI、React/Vite、PostgreSQL 和 `GameEngine` 主边界。
- 不恢复自由文本主入口、旧 CLI/REPL、HP/MP 或已删除境界。
- 不新增独立资源经营系统、通用内容管理平台或工作流引擎。
- 当前实现局长与长期产品局长分开记录；完整局验收以规则终局为准，不把固定回合数永久写死为产品定义。

### 2.2 权威状态

- 规则引擎决定境界、寿元、伤势、死亡、奖励、属性和其他权威结果。
- 模型只负责叙事与选项表达，不得覆盖规则结果或重置世界、身份和主线。
- 关键道具、功法、称号、关系、伤势、寿元、境界和终局必须结构化落账。
- 传闻、见闻和外界局势可以只进入世界情报，不得伪装成玩家已获得资源。
- 叙事与结构化状态不一致时，必须拒绝、压制或自然改写。

### 2.3 内容与存档

- 仓库内版本化内容是剧情创作源；Python 负责选择、规则和结算。
- Session 与存档只保存内容键、精确版本和可变进度，不复制不可变定义。
- 旧存档按精确版本解析，不得因内容更新静默换线。
- PostgreSQL 内容表在具备完整发布、迁移和回滚流程前，不作为第二套运行时真值源。

### 2.4 模型与 fallback

- Narrator 必须返回完整叙事和四项固定语义选项；权威状态只来自 `ChoiceIntentV1 -> RuleTurnOutcomeV1`。具体传输格式由 provider adapter 决定。
- 缺少正文或选项、结构残留、英文状态词或无效选项均属于契约失败；兼容 `state_update` 只作诊断。
- gameplay recovery 与 provider fallback 分开记录；两者都不能冒充严格 live-model 成功。
- repair 不作为普通回合常态路径；必要重试、repair 和 Judge 必须脱敏记录。
- 不记录原始 prompt、原始响应、凭据或用户隐私。
- 本地模型验证复用普通 Web 应用和 PostgreSQL 系统模型配置；调用次数、费用和临时浏览器汇总只作记录，不形成第二个运行面。

### 2.5 UI 与交互

- 纯视觉任务限定在表现层，不借机修改 API、玩法规则或 Session 结构。
- 视觉任务必须指定权威原型或 artifact manifest，不在长期目标中绑定本机绝对路径。
- 关键按钮覆盖默认、悬停、按下、键盘焦点、禁用和加载状态。
- 关键流程支持键盘、减少动效、移动端溢出和重复提交防护。
- 冲突、加载、空状态、错误、长文本和存读档必须有明确玩家反馈。

### 2.6 可靠性与安全

- 用户、会话、存档、回合和终局奖励的跨表写入必须有事务与幂等边界。
- 修改请求使用版本或幂等键；多实例部署不得依赖进程内唯一状态。
- 自定义模型地址必须经过协议、主机、DNS、IP、重定向和连接目标校验。
- 应用校验、出站 ACL、入口限流和反向代理分别解决不同风险，不得互相替代。
- secret 不进入代码、日志、文档、存档、前端包或浏览器证据。
- 迁移必须覆盖空库、已有库、异常数据、备份和可执行回滚方案。

## 3. 治理原则

- 先修玩家可见缺陷、安全、数据一致性和发布阻塞，再处理维护性债务。
- 优先治理真实调用路径，不以文件长度、删除行数、拆分数量或测试数量作为成果。
- 复用现有框架、标准库和稳定依赖；只有在确有重复职责时才增加抽象。
- 兼容 wrapper、协议适配和防御性逻辑必须先确认调用者与替代路径，再决定删除。
- 大文件按职责小步拆分，每次保持外部 API、schema 和存档兼容。
- 发现重复状态源时明确唯一权威源，禁止通过双写长期维持表面一致。

## 4. 交付优先级

| 级别 | 定义 |
| --- | --- |
| P0 | 高危安全、数据损坏、不可逆迁移或核心流程阻塞 |
| P1 | 阻止真实玩家验收的契约、状态、内容或关键交互问题 |
| P2 | 不阻塞当前功能，但持续增加维护、性能或体验成本 |
| P3 | 文档、仓库、产物和流程清理 |

P0 随时抢占。没有 P0 时，按 `NEXT_GOVERNANCE_BACKLOG.md` 中经过证据确认的依赖顺序推进。

## 5. 验收原则

### 5.1 代码与数据

- 执行 README 与 CI 定义的编译、静态检查、非 live 测试和前端门禁。
- PostgreSQL 测试必须零 skip；缺环境造成的跳过不算通过。
- 数据库变更验证迁移、事务、幂等、备份和恢复。
- 外部 API、schema 和存档格式保持兼容，或提供明确迁移。

### 5.2 浏览器与模型

- 玩法、状态落账、模型契约或核心交互变化后，在现有本机项目数据库串行执行真实浏览器验收；验收前先备份，因为测试可能清空应用表或重建 schema。
- 垂直切片验证连续推进、内容质量、状态一致性、存读档和异常交互。
- 长局运行至规则终局，验证主线持续、路线差异、寿元压力、突破、失败恢复和结局。
- live-model 必须同时满足请求成功、Narrator 契约完整、无 provider fallback、无 gameplay recovery。
- 性能报告至少包含样本数、p50、p95、最大值、超时数及 Narrator/repair/Judge 耗时。

### 5.3 证据边界

- 每次基线记录 commit、工作树状态、日期、环境和证据路径，不混用 HEAD 与未提交工作树。
- Chrome 数据库不得与 `tests\web` 共用并发测试库。
- 浏览器临时汇总默认写入系统临时目录，或显式指定的仓库外目录；脚本拒绝仓库内输出路径。
- 当前事实只写入 `PROJECT_AUDIT.md`，未完成项只写入 `NEXT_GOVERNANCE_BACKLOG.md`。
- 本地通过不等于生产通过；HTTP 200、fallback 或历史记录不能替代当前生产验收。

## 6. 强阻塞规则

出现以下情况时停止当前批次并报告已完成项、未完成项、证据、影响和解除步骤：

- 必须读取或暴露 secret 才能继续。
- 发现可能导致数据损坏、不可逆迁移或高危安全问题。
- 用户现有修改与目标文件冲突且无法安全合并。
- 产品方向、生产状态或迁移策略无法从可验证事实判断。
- 必要外部环境不可用，且不能用本地或模拟验证替代。

任何 P0 未清零时不得发布。P1 只有在用户明确批准残余风险和发布边界后，才可带入受限试玩。
